# 오픈소스 결정 기록

검증 기준일: 2026-10-29. 수치는 `gh api repos/<repo>`로 읽은 값이다. 라이선스 원문은 앞부분만 읽은 항목이 있어 "미확인"으로 표시했다.

## 2026-10-29 영상 렌더 엔진 (컷 이미지 + 음성 + 자막 + 음악 → 9:16 mp4)
- 제약: 서버에서 다중 사용자 렌더, 상업 서비스, 한국어 자막, 소수점 단위로 부드러운 카메라 이동.
- 후보:
  - FFmpeg + Pillow 직접 구성 (현재 `build_v2.py`) — 외부 라이브러리 추가 없음
  - MoviePy — MIT, ★15,052, 마지막 push 2026-08-26
  - Remotion — ★68,711, push 2026-10-28, 라이선스 `NOASSERTION`(자체 라이선스)
  - editly — MIT, ★5,571, 마지막 push 2025-05-12
- 채택: **FFmpeg(서브프로세스) + Pillow 직접 구성 유지**
  - 이유: 이미 동작하고, 흔들림을 측정해 검증했다(떨림 0.073→0.0007px). MoviePy와 editly가 줄여줄 코드가 거의 없고, 둘 다 프레임 단위 소수점 카메라를 직접 지원하지 않는다.
- 버린 후보와 이유:
  - Remotion: 무료 라이선스는 개인, 직원 3명 이하 영리 조직, 비영리, 평가 목적에 한정된다. 그 이상은 회사 라이선스가 필요하다. 다른 사람에게 렌더를 제공하는 서비스가 무료 범위에 드는지는 원문에서 확인하지 못했다. 5.0에서 약관이 바뀐다고 적혀 있다. 라이선스 불확실성이 크다.
  - editly: 마지막 업데이트가 5개월 전이고 기능이 얇다.
  - MoviePy: 필요한 부분을 이미 구현했다. 나중에 편집 UI가 필요하면 재검토.
- 라이선스 주의:
  - FFmpeg는 기본 LGPL 2.1+, `--enable-gpl`로 빌드하면 GPL v2+가 된다. libx264를 쓰는 빌드는 GPL일 수 있다(빌드 구성은 미확인).
  - 서버에서 별도 프로세스로 호출하고 바이너리를 사용자에게 배포하지 않으면 보통 배포 의무가 생기지 않는다. 데스크톱 앱으로 배포하게 되면 다시 검토한다.
- 적용 후 확인: 서버 렌더 시간 측정(이 PC 기준 21컷 약 5분 21초), 동시 2작업 부하 테스트.

## 2026-10-29 작업 큐 (이미지/음성/렌더 비동기 작업)
- 제약: Python 백엔드, 재시도와 취소, 비용 상한, 초기에는 인프라를 적게.
- 후보:
  - Postgres 작업 테이블 + 워커(`FOR UPDATE SKIP LOCKED`) 직접 구현
  - Celery — ★29,096, push 2026-10-28, SPDX `NOASSERTION`(LICENSE 앞부분 저작권 고지만 확인, 라이선스 종류는 미확인)
  - BullMQ — MIT, ★9,558 (Node 전용)
  - Temporal — MIT, ★24,054 (운영 부담 큼)
- 채택: **MVP는 Postgres 작업 테이블 직접 구현**, 규모가 커지면 Celery로 이행
  - 이유: 이미 필요한 Postgres만으로 되고(Supabase), 작업 종류가 5개뿐이라 100줄 안팎이다. Redis 같은 인프라를 늘리지 않는다.
- 버린 후보와 이유: BullMQ는 Node 전용이라 Python 렌더 코드와 맞지 않는다. Temporal은 MVP에 과하다.
- 라이선스 주의: Celery를 쓰게 되면 라이선스 원문 전체와, 브로커로 쓸 Redis의 라이선스 변경 이력(Valkey 같은 대안)을 확인한다. 이 부분은 미확인.

### ruff (lint)
- 규칙 `E W F I B UP SIM RUF`로 37건 → 0건. 자동 수정 17건과 수동 수정(쓰이지 않던 변수 `e`, 애매한 변수명 `l`, 길이 초과 줄, `zip(strict=True)` 등).
- **의미 없는 테스트 1개 발견:** `test_fonts`의 "없는 폰트" 테스트가 `try/except: pass`라 항상 통과했다. 폴백 폰트를 쓰거나 명확히 실패하는지 검증하도록 교체.
- 동작 불변 확인: 린트 이전(커밋 HEAD)과 이후 코드로 같은 3컷을 렌더해 샘플 프레임 평균 픽셀 차이 0.0000.
  (처음 비교에서 3.99가 나온 것은 비교 기준 영상이 Pretendard 폰트 도입 이전 렌더였기 때문이다.)

### Playwright (브라우저 E2E)
- 가짜 이미지·음성·렌더 제공자로 띄운 전용 API(`tests/e2e_server.py`)와 별도 폴더(`.next-e2e`)에 빌드한 프론트엔드를 대상으로 11개 시나리오(목록, 카드, 편집·저장·새로고침 유지,
  자막 칩, 무음 컷, 비용 확인·취소, 재생성, 목소리 샘플, 잘못된 속도, 렌더, 없는 프로젝트, 이미지 확대). 유료 서비스와 실제 키는 쓰지 않는다.
- **약한 단언 발견:** 처음 버전은 자막 끊기를 일부러 망가뜨려도 통과했다. `getByText`가 자막 칩뿐 아니라 같은 단어가 들어 있는 입력칸(textarea)에도 맞았기 때문이다.
  칩만 골라 전체 내용을 목록으로 비교하도록 고친 뒤, 같은 변형(자막 한 줄 한도 축소)에서 2개 테스트가 실패함을 확인했다.
- 일시적인 `spawn EPERM`(Windows 프로세스 실행 거부)이 한 번 있었고 재실행으로 통과했다.

### OpenCV + YuNet + SFace (얼굴 일관성)
- `face-check`: 각 컷의 모든 얼굴을 기준 인물들과 비교해 배정하고, 어떤 기준과도 안 맞는 얼굴은 `drift?`, 얼굴 높이 80px 미만은 `small`로 구분한다.
- **첫 구현의 결함을 실데이터로 발견·수정:** 가장 큰 얼굴만 비교해서 한 화면에 두 사람이 나오는 컷 7·12에서 알바생을 할아버지와 비교해 가짜 "다름"이 나왔다.
- 실제 결과(기준: 할아버지 컷 5, 알바생 컷 13, 기준 코사인 0.363): 일치 8컷(0.44~0.86), 얼굴 없음 4컷, 판정 불가 2컷(얼굴 61~62px), `drift?` 3컷(컷 18, 21, 25).
  세 컷을 눈으로 대조하니 모두 옆모습·뒷모습·위에서 내려다본 각도였고 옷·머리·안경은 같았다(컷 21은 0.357로 기준에 근소 차이).
  **정면 얼굴에서는 신뢰할 수 있고, 각도가 큰 컷은 보수적으로 의심 표시를 하는 도구**다. 자동 불합격 판정에는 쓰지 않고 사람이 볼 컷을 고르는 용도로 쓴다.
- 임계값 0.363은 OpenCV가 공개한 사진 기준 값이라 생성 이미지에는 맞지 않을 수 있다.

### 서비스 배포 전 라이선스 점검 (2026-11-05)
`.venv`에 설치된 실제 패키지의 메타데이터와 동봉 라이선스 파일로 확인했다(법률 자문이 아님).
- **opencv-python-headless 5.0.0.93:** 휠 포장은 MIT, OpenCV 본체는 Apache 2.0. 휠에 FFmpeg(LGPL 2.1, 동적 DLL로 분리), libpng·libwebp·libjpeg-turbo·protobuf·OpenJPEG(BSD 계열),
  Intel IPP(Intel Simplified Software License, 재배포 허용·조건 있음)가 같이 들어 있다. 우리는 얼굴 인식(dnn)과 이미지 디코딩만 쓰며 영상 입출력(VideoIO)은 쓰지 않는다.
  서버에서 돌리기만 하면 문제 없고, 바이너리를 배포(데스크톱 앱 등)한다면 `LICENSE-3RD-PARTY.txt` 동봉과 LGPL 고지가 필요하다.
- **YuNet(MIT), SFace(Apache 2.0):** 모델 파일과 라이선스 사본을 `assets/models/`에 둔다.
- **더 큰 쟁점 — imageio-ffmpeg의 ffmpeg 바이너리:** imageio-ffmpeg 0.7.0 자체는 BSD-2-Clause이지만 번들 ffmpeg(gyan.dev 7.1 essentials)는 `--enable-gpl --enable-libx264 --enable-libx265`로 빌드된 **GPL 빌드**다.
  - 서버에서 실행만 하고 바이너리를 배포하지 않으면 GPL 배포 의무는 생기지 않는다. 사용자에게 설치형으로 배포하면 GPL 소스 제공 의무가 생기므로 그때는 LGPL 빌드로 바꾸거나 소스를 제공해야 한다.
  - H.264(x264) 인코딩은 특허 풀(MPEG LA 등) 이슈가 별도로 있다. 상용 서비스 전에 확인이 필요하다.
- 결론: **호스팅형 서비스로 운영하는 한 현재 구성은 진행 가능**하다. 설치형 배포나 상용 출시 전에는 ffmpeg 빌드(LGPL 대체)와 H.264 특허를 먼저 정리한다.
