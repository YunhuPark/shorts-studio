# Phase 1 계획: 로컬 대시보드 → 다중 사용자 서비스 뼈대

기준: [mvp-design.md](mvp-design.md) 3·6·7·10절. 현재 상태는 단일 사용자 로컬 대시보드(파일 저장, 프로세스 내 작업 관리자)다.

## 원칙
- 한 단계가 끝날 때마다 기존 테스트(단위 93개, E2E 12개)가 그대로 통과해야 한다. 로컬 모드는 계속 동작한다.
- 외부 서비스 가입·키 발급·결제 설정은 **사용자가 직접** 한다. 계정 생성과 결제 정보 입력은 대신하지 않는다.
- 단계마다 유료 호출 없이 가짜 제공자로 검증하고, 실제 호출은 마지막에 한 번만 한다.

## 단계
| # | 작업 | 사용자 준비 | 완료 기준 |
|---|---|---|---|
| 1 ✅ | **저장소 추상화:** `ProjectStore`를 인터페이스로 분리(파일 구현 유지) + 모든 프로젝트에 `owner` 필드. 경로 조작·소유자 검사 테스트 | 없음 | 로컬 테스트 통과, 다른 owner의 프로젝트는 404 |
| 2 ✅ | **작업 큐 분리:** 프로세스 내 `JobManager` → 상태를 DB(처음엔 SQLite)에 저장하는 큐 + 별도 워커 프로세스. 재시작해도 작업 상태 유지, 중복 실행 방지 | 없음 | 워커를 죽였다 살려도 작업이 이어지거나 실패로 표시 |
| 3 (백엔드 ✅, 프런트 로그인 남음) | **인증:** Supabase Auth(이메일/구글) JWT 검증 미들웨어. 로컬 모드는 고정 사용자 | Supabase 프로젝트 생성, URL·anon key·JWT secret을 환경변수로 전달 | 토큰 없으면 401, 다른 사용자 데이터 접근 불가 |
| 4 | **저장소를 Postgres·Storage로:** 1단계 인터페이스의 두 번째 구현. 이미지·영상은 Storage, 서명된 임시 링크로 다운로드 | 3단계의 Supabase 프로젝트 | 같은 테스트가 두 구현에서 모두 통과 |
| 5 ✅ | **크레딧 원장:** 현재 `spend.jsonl`을 사용자별 원장 테이블로. 예약→확정/환불, 사용자별 일일 한도, 월 예산 중단 스위치 | 단가 정책 결정 | 동시 요청에서도 한도 초과 없음(경쟁 조건 테스트) |
| 6 (AI 표시 ✅, 입력 검수 기본형 ✅) | **AI 표시와 입력 검수:** 영상 모서리 표식 옵션 + mp4 메타데이터, 스토리보드 생성 전 입력 분류 | 과기정통부 가이드라인 원문 확인(법률 검토) | 표식 켠 렌더에서 프레임과 메타데이터 확인 |
| 7 | **결제(토스페이먼츠):** 크레딧 충전, 웹훅 검증, 환불 | 사업자 등록, 토스 가맹 계약, 테스트 키 | 테스트 모드 결제→크레딧 증가→웹훅 중복 수신에도 한 번만 반영 |

1~2단계는 외부 가입 없이 바로 시작할 수 있다. 3단계부터 사용자 준비가 필요하다.

## 열려 있는 결정 (단계 진행 전에 필요)
- 단가: 편당 원가(대략 $1.5~$5.5)의 몇 배로 팔지, 구독인지 크레딧 팩인지 (5·7단계)
- 목소리 공급자: Azure만으로 갈지 ElevenLabs를 서비스에 쓸 수 있는지(약관·계약 확인)
- 출시 형태: 호스팅형(현재 구성으로 가능) vs 설치형(ffmpeg GPL 빌드와 H.264 특허 정리 필요, open-source-decisions.md 참고)

## 위험
- 동시 사용자가 늘면 렌더(CPU)가 병목이다. 워커당 동시 1~2작업으로 시작하고 큐 길이를 노출한다.
- 이미지 공급자 가격·모델명이 바뀐다. 모델명은 설정값으로 두고 `models.list`로 확인한다.

## 단계 2 결과 (2026-11-05): 작업 큐를 DB와 워커로 분리
- `api/jobqueue.py`(SQLite, 표준 라이브러리) · `api/worker.py` · `api/handlers.py`. 작업은 `{kind, project, owner, params}` 행이고,
  워커는 가장 오래된 대기 작업을 원자적으로 가져가(`BEGIN IMMEDIATE`) 하트비트를 보내며 실행한다. 하트비트가 60초 끊긴 실행 중 작업은 실패로 바꾸고
  이미지 재생성이면 예약했던 비용을 환불한다(한 번만).
- API 프로세스 안의 스레드 워커(기본)와 별도 프로세스 워커(`serve --no-worker` + `worker`)가 같은 큐를 쓴다. 별도 프로세스에서 작업이 실제로 도는 것을 테스트로 확인했다.
- 테스트: 큐·워커 12개, API 3개(재시작 후 상태 유지, 죽은 워커의 작업 실패·환불, 워커 없는 API는 대기 상태 유지). 변형 검증: 오래된 작업 복구 제거(4개 실패),
  하트비트 제거(1개 실패), 환불 제거(1개 실패), 이미 가져간 작업 재선택(2개 실패)에서 테스트가 실패함을 확인했다.
- **한계:** `BEGIN IMMEDIATE`가 두 워커의 동시 claim을 막는다는 점은 테스트로 증명하지 못했다(락 없이 `BEGIN`만 써도 우리 테스트는 통과). 코드의 의도로 두었다.
  SQLite는 한 서버(한 디스크)에서만 공유된다. 여러 서버로 늘리면 Postgres로 옮겨야 한다(4단계).
- 지출 장부(`spend.jsonl`)는 API와 워커 프로세스가 같이 추가 기록했다. 5단계에서 SQLite 원장으로 바꿨다(아래).

## 단계 3 결과 (백엔드, 2026-11-06): 로그인 토큰 검증
- `api/auth.py`: Supabase 로그인 토큰(JWT)을 검증해 사용자 id(`sub`)를 소유자로 쓴다. 공유 비밀(HS256) 또는 공개키(ES256/RS256, JWKS) 방식을 **설정이 정하고 토큰은 정하지 못한다**
  (알고리즘 `none`·공개키를 HMAC 비밀로 쓰는 알고리즘 혼동 차단). 만료·audience 필수, issuer는 설정 시 검사. 라이브러리는 PyJWT(MIT, 선택 설치 그룹 `auth`).
- `/api/health`만 열려 있고 나머지(설정, 목소리 샘플, 자막 미리보기 포함)는 모두 토큰이 필요하다. 비밀 값이 없으면 로컬 단일 사용자 모드 그대로.
- 테스트 11개(가짜 키·토큰을 직접 발급). 변형 검증: audience, 만료, issuer, 알고리즘 혼동, 서명 검증을 각각 끄면 테스트가 실패함을 확인했다.
- **남은 일(3b, 프런트):** Supabase 로그인 화면과 토큰 첨부, 그리고 `<img>`·`<video>` 태그는 Authorization 헤더를 못 보내므로 이미지·영상은 쿠키 또는 서명된 임시 주소로 바꿔야 한다.
  Supabase 프로젝트가 있어야 실제 로그인을 검증할 수 있다(사용자 준비).
- **미검증:** 실제 Supabase 토큰으로는 아직 시험하지 못했다. JWKS 가져오기(`PyJWKClient`)는 가짜 키 클라이언트로만 검증했다.

## 단계 5 결과 (2026-11-06): 사용자별 크레딧 원장
- `api/ledger.py`(SQLite): 금액은 정수 마이크로달러로 저장해 합계가 어긋나지 않는다. `reserve`는 사용자 일일 한도와 선택적 전체 월 예산을 **하나의 쓰기 트랜잭션**에서 검사·기록하므로
  빠른 연타, API 스레드, 별도 워커 프로세스가 동시에 와도 한도를 넘지 않는다. `refund`는 예약 id로 **멱등**이다(실패 작업 환불과 죽은 워커 복구가 겹쳐도 한 번만).
  환불은 예약한 날짜로 기록해 그날 합계가 0이 되게 한다. 기존 `spend.jsonl`은 'local' 소유자의 기록으로 한 번 이관한다.
- 한도: 사용자별 일일(`SHORTS_DAILY_CAP_USD`)과 전체 월 예산(`SHORTS_MONTHLY_CAP_USD`, 0이면 끔) — 월 예산에 닿으면 모든 사용자의 유료 작업이 멈춘다(중단 스위치).
- 이전의 `spend_lock`(한 프로세스 안에서만 유효)은 필요 없어져 없앴다.
- 테스트: 원장 13개(스레드 12개 동시, **별도 프로세스 3개 동시**에서 정확히 6건만 성공, 동시 환불 8개가 1건), API 4개(사용자별 한도, 실패 시 올바른 사용자에게 환불, 월 예산, 같은 컷 연타는 한 번만 청구).
  변형 검증: 한도 검사 제거(6개 실패), 락 없는 `BEGIN`(3개 실패 — 큐와 달리 여기서는 동시성 테스트가 잡는다), 환불 멱등 제거, 환불 날짜, 월 예산, 사용자 구분 제거, 실패 시 환불 제거를 각각 확인했다.
- **한계:** 금액은 설정 단가로 계산한 추정이며 실제 청구액이 아니다. 사용자가 구매하는 "크레딧" 단위(원화·충전)는 7단계(결제)에서 이 원장 위에 얹는다. SQLite라 서버 한 대 기준이다.

## 단계 6 결과 (AI 표시, 2026-11-06)
- `render/label.py`: 왼쪽 위에 "AI 생성" 둥근 표식(Pillow로 한 번 그려 ffmpeg `overlay`로 전체 길이에 입힘)과 mp4 `comment`/`description` 메타데이터. 끈 상태의 최종 ffmpeg 명령은 기존과 **글자 그대로 같다**(테스트로 고정).
- 대시보드는 기본으로 켜져 있고(렌더 패널 체크박스) 끌 수 있다. CLI는 `--ai-label`로 켠다. 라이브러리 기본은 꺼짐(기존 출력 동일 유지).
- 테스트 6개 + API 1개 + 브라우저 1개: 실제 ffmpeg로 표식 있는/없는 영상을 만들어 **표식 자리는 크게 다르고 나머지 화면은 같음**, 메타데이터에 문구가 있음/없음, 오디오 유지를 확인했다. 변형 4가지(위치, 메타데이터, 오버레이 제거, 기본 명령 변경) 모두 테스트가 실패함을 확인했다.
- **법적 확인 필요(내가 확정할 수 없음):** 표식의 문구·크기·위치·표시 시간이 인공지능기본법 시행령·과기정통부 가이드라인과 각 플랫폼(YouTube 합성 콘텐츠 공개 등)의 요건을 만족하는지는 원문 확인이 필요하다.
  YouTube의 "변경되거나 합성된 콘텐츠" 설정은 업로드할 때 사용자가 직접 체크해야 하며 이 표식이 그것을 대신하지 않는다.
- **남은 것:** 입력 검수(실존 인물·아동 부적절·폭력·혐오 분류)는 분류 모델 선택(오픈소스/API)과 정책 결정이 필요해 아직 하지 않았다.

## 단계 6 결과 (입력 검수 기본형, 2026-11-12)
- `safety.py`: 제목·설명·대사·장면 문장을 한 번 훑는 **투명한 단어·패턴 검사**. 오류(차단): 성적 표현, 미성년자+성적 표현의 조합, 자해·자살 방법, 폭탄·마약 제조법, 딥페이크·보이스피싱 등 사기.
  경고: 잔인한 묘사(고어 등). 차단되면 이미지 재생성(비용 예약 전)과 렌더가 422로 거절되고 설명이 나온다. 초안 저장은 막지 않고 점검 결과에 표시된다.
- 전각 문자·보이지 않는 문자·대소문자는 정규화한다. 영어는 단어 경계, 한국어는 부분 문자열로 매칭하고 `누드김밥`, `naked eye` 같은 일상어는 예외로 둔다.
- 테스트 16개 + API 4개: 분류별 차단, 오탐 방지(일상 문장 14개와 예제 스토리 전체), 우회(전각·제로폭), 차단·경고 구분, 비용 예약 전 차단. 변형 8가지(조합 규칙 제거, 예외 제거,
  정규화 제거, 영어 부분 일치, 경고도 차단, 재생성·렌더 게이트 제거, lint 제외) 모두 테스트가 실패함을 확인했다.
- **한계(중요):** 키워드 검사는 의도·문맥·혐오 표현·괴롭힘·실존 인물 여부를 판단하지 못하고, "p o r n"처럼 풀어 쓰면 통과한다(테스트로 명시). 혐오 표현 목록은 욕설을 저장소에 쓰지 않으려고 넣지 않았다.
  이미지·음성 제공자의 자체 안전 필터가 2차 방어선이다. 서비스로 공개하려면 학습된 분류기, 신고 창구, 사람 검토가 필요하고 **금지 기준과 단어 목록은 서비스 운영자가 검토·확정**해야 한다.
